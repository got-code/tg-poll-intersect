# Development rules

- Agree on a plan before implementation. Keep product copy English and branding neutral.
- Follow established industry practices appropriate to the project: Clean Architecture, SOLID, KISS, YAGNI, DRY, security and privacy by design, accessibility, automated testing and reproducible builds. Keep domain logic independent of UI and infrastructure. Organize code around clear responsibilities and reasons to change, with high cohesion and low coupling. Prefer simple designs; verify these principles during implementation and review.
- Structure: group code that changes for the same reason in `src/modules/<feature>`, with `domain`, `application`, `infrastructure`, and `presentation` inside as needed. Keep feature-specific adapters, styles, and view state in their module. Name files by responsibility, omitting redundant module names. Root layers contain shared contracts, technical helpers, and UI primitives. Avoid cycles, empty layers, and speculative shared abstractions.
- Module boundaries: a feature module is a directory under `src/modules`; root shared code and external libraries are not other feature modules. Within a feature, direct imports follow the layer rules. Feature infrastructure may reuse root shared infrastructure; shared code must not depend on features. Dependencies between features use the provider's `index.ts` core API, never its internal adapters or UI. For application assembly, `main.ts` wires concrete implementations and `presentation/app.ts` connects feature UI entry points; these two composition files may import the respective module entry points directly, while still obeying layer rules.
- Layers: `domain` owns models and business rules; `application` owns workflows, ports, and preparation of safe export data; `infrastructure` owns external integrations and their technical helpers; `presentation` owns user interaction and output formatting, including CSV. Domain and application must not depend on infrastructure or presentation; presentation and infrastructure communicate through application contracts. Keep browser and SDK details outside the core, and enforce layer and module boundaries in automated checks.
- Data boundaries: adapters map storage, transport, SDK, and UI representations to the declared application contracts. Application validates use-case inputs and owns scenario defaults; domain enforces model invariants and may parse domain-defined values. Determine ownership by the knowledge a function contains, including pure helpers; `Number()` or `trim()` alone does not determine its layer. Keep display labels and dialog state in presentation. Review semantic ownership as well as import direction.
- Loading: keep Telegram SDK code outside the initial static import graph. Preload it when the login dialog opens, sharing pending loads with sign-in and unlock. Loading code must not create a client or connect an account. Handle load failures and cancellation, including destroying clients created after an attempt was cancelled.
- Prefer established tools and libraries over custom implementations. Write custom code only when existing solutions demonstrably do not meet the requirements.
- Preserve the privacy and storage contracts, locked dependencies and bundled license notices. Preserve safe error provenance (service, RPC code/status, and timing) and explain specific known failures. Use an unknown-cause fallback only when the cause is unavailable; never expose raw payloads, credentials, or identifiers in error messages or diagnostics.
- Keep every necessary test in the repository as automated code; remove temporary scripts. Run checks proportionate to the change and its affected dependencies. Skip checks that demonstrably cannot be affected. Use the full suite for broad or uncertain changes, project-wide validation, or release checks. State what was verified.
- Keep documentation brief and operational; avoid duplicating implementation details or platform documentation.
- Maintain these rules when requirements change. Put shared requirements here and agent-only instructions in `AGENTS.md`.
